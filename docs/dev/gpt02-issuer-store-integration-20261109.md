# GPT02 DEV: dedicated issuer evidence-store integration

## Delivered in this change

`artifacts/api-server/src/lib/gpt02-issuer-store.mjs` implements separate connection configuration and a transactional evidence-store client. It does not import the application's database pool. A missing issuer DSN is an error, not a fallback to `SUPABASE_DATABASE_URL_DEV` or `postgres`.

The attestor records an Ed25519-signed, command-bound approval envelope. The issuer independently checks that signature with a server-configured public key before consuming the stored approval. The key is never accepted from the request. The stored envelope, signature and digest must match exactly. No signing private key is generated by the runtime module.

Each transaction validates both `current_user` and `session_user`, role attributes, absence of role membership/global-data access, absence of CREATE privileges, and absence of direct evidence-table privileges. Transactions have statement/lock timeouts; failures roll back; the connection is destroyed before returning it to the pool. A receipt is returned only after COMMIT.

Configuration requires explicit DEV markers, a dedicated role, an independently pinned host/database and certificate-verifying TLS. These are new candidate settings, not changes to the running Hub environment. The current configuration accepts direct role usernames; live network/TLS and hosted role provisioning have not been verified by this test.

## Actual isolated integration results

Executed on the authorized VPS in a disposable PostgreSQL 16.15 container and a Node 24 container. Both have `--network none`, no published ports, and communicate only through a private, temporary Unix-socket volume. Random fixture passwords are required by SCRAM-SHA-256. Neither container receives CST DEV/PROD credentials. The store-owner role is NOLOGIN, NOSUPERUSER, NOBYPASSRLS. The two private tables have FORCE RLS and append-only triggers. Only narrowly scoped SECURITY DEFINER functions run as this nonprivileged owner; no function is owned by `postgres`. PUBLIC has no function access. Each LOGIN receives only its own function's EXECUTE privilege and schema USAGE.

**21 behavioral scenarios passed**, exit 0. Node reports 22 tests because it includes the parent test. Covered scenarios:

- Distinct real LOGIN/session identity and rejection of a wrong password.
- No application-DSN fallback; DEV/role/host/database pinning and TLS configuration checks.
- No elevated role attributes, memberships, PUBLIC execution, cross-role function access, unrelated-table reads or direct evidence DML/DDL.
- Bad signatures, caller-supplied public keys, unknown fields, Task 135, PROD, invalid/expired claims rejected before writing.
- Valid signed approval persistence; duplicate record rejection; exact command/task/company/operator/attempt/nonce binding.
- Eight concurrent requests yield one committed receipt; later replay is denied.
- Explicit transaction rollback leaves no receipt and allows a subsequent valid consume.
- Injected database failure rolls back, does not consume the nonce and returns a sanitized error.
- Expiry is rechecked after waiting on the approval row lock.
- A postgres session using SET ROLE is rejected because the original session identity is wrong.
- Accidental table access or owner-role membership causes the connector to stop before consumption.
- Append-only evidence mutation is denied.

The test implementation is `scripts/dev/gpt02-issuer-store.integration.test.mjs`; the runner is `scripts/dev/test-gpt02-issuer-store-isolated.sh`. The fixture SQL refuses any database name except `gpt02_issuer_isolated`. Containers, socket volume and temporary passwords are cleaned on exit. CI runs this integration suite alongside existing regressions.

## What this does NOT prove or enable

This component is not imported into an HTTP route and is not deployed. No new role, schema, password, environment variable or connection was installed in live DEV. The existing PR #156 runtime was not replaced. No new application task or Core command was created, Task #135 was not retried and no PROD service was changed.

`authorizationGranted` and `dispatchPermitted` remain false on both returned evidence results. A committed evidence receipt is not a worker grant, lease or native final ACK. Fixture approvers/signatures are synthetic and do not represent the user's real Super Admin approval or Google verification.

The SQL fixture is not a live migration. Its record function relies on the isolated attestor service to verify the signature; PostgreSQL does not itself verify Ed25519 here. A compromised attestor/issuer service or a database administrator remains outside the protections proven by these tests. In particular, placing the store in a cluster still writable by the general Hub administrative login would NOT close that trust boundary. Live deployment requires a separately reviewed owner/role/credential boundary, real authenticated operator and command binding, hosted readback, rollback and lease/native-worker evidence. Do not copy the fixture into CST-DEV or change the Hub's database connection based on this test.

**Result: isolated issuer connection + signed evidence persistence integration PASS. Live cutover and native GPT02 E2E remain NO_GO.**
