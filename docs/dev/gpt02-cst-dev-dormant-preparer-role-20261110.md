# CST-DEV GPT02 preparer: first inactive role staging, no login or runtime permission

## Exact scope

Only CST-DEV Supabase project `xssrfshdrtdfupgqwfdw` and database `postgres`. Create the named **dormant** PostgreSQL role `gpt02_core_prep_login` **without any database login or password**, and without changing the Hub's current `postgres` connection, application tables, existing user/PIC rows, Core task/Hub execution, claims, approvals, nonce receipts or issuer secrets. No PROD mutation or DELL worker send. The role name is reserved for a future separate GPT02 preparer, not an activated service account.

SQL: `scripts/dev/gpt02-core-preparer-role-dormant.sql`. DDL requires `current_user=postgres`, database `postgres`, and a write transaction. It creates the role with explicit `NOLOGIN`, `NOINHERIT`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, `CONNECTION LIMIT 0`, `PASSWORD NULL` and an expiration in the past (`2000-01-01`). It does **not** create a schema, function, role membership, credential or grant. Reapplying the exact DDL is a no-op only if the role is still inactive with these guarantees; if an existing role has been enabled/escalated or made a member of another role, the SQL fails without modifying its credentials. No password is printed or rotated.

A new role may inherit database or schema `PUBLIC` rights from the host cluster when later enabled: the current read-only audit showed `PUBLIC` schema USAGE but no PUBLIC SELECT/INSERT on shared `public`, `ai_platform` or `gpt02_private` relations. This staging step is **not** a proof of full effective table privileges. That requires a separately authenticated connection with its own valid role and a reviewed private function/extension boundary. It is intentionally impossible to connect as the staged role until a separate authorized change passes.

## Test evidence required before any hosted application

The exact DDL was applied twice to a disposable PostgreSQL16 container with `--network none`: the first creates one disabled role; the second is idempotent; catalog readback proves NOLOGIN, NOINHERIT, no elevated privileges, connection limit 0, expiry in the past and zero outgoing role memberships. Synthetic `public.ai_tasks` / `ai_platform.ai_coding_bridge_commands` had no direct SELECT/INSERT/UPDATE/DELETE for the role. A deliberately modified `LOGIN` role was rejected without repair or password rotation. A wrong-database DDL attempt was also rejected. Neither test container can access the CST-DEV/PROD network or credentials.

`gpt02-lifecycle-live-preflight.cjs` now reports `roleState.dormantPreparerStaged` separately from `roleState.preparerDedicated`. A dormant NOLOGIN role is **not** an active dedicated preparer, does not remove issuer/lease/signature blockers and never changes `releaseDecision=NO_GO`. Its exact role state is obtained via one certificate-verified `BEGIN READ ONLY` query against the pinned CST-DEV project. Unit coverage checks that distinction. CI adds the new dormant-role PostgreSQL fixture to an **existing** job step without creating extra workflow jobs or relaxing the existing lifetime/Task135/136 guards.

## Explicit NOT DONE after this phase

No app or worker changes its connection string. No `gpt02_stage` live database schema/function is created; no `dev_gpt02_attestor_evidence` / `dev_gpt02_issuer_evidence` role is enabled. No PIN/OTP/password changes occur. The existing signed operator approval, nonce and lease remain **only** offline, synthetic evidence. Task135 must never be replayed and completed Task136 retains its original one-shot native response/ACK. Full lifecycle remains **NO-GO** and the HTTP prepared-state and lifecycle gates remain active. A later activation must introduce an independent scoped login *without reusing the deprecated live password-rotation smoke*, review the private SQL function's actual privileges and caller identity, and prove one separately authorized new DEV command through native ACK.
