## Verified ambient Supabase maintainer read privilege

The first hosted migration attempt failed atomically at its final ACL check, while creating no sidecars and leaving the original owner grantor graph intact. Direct catalog audit identified the reason: the shared `postgres` account is a non-superuser but has effective `pg_read_all_data`, `BYPASSRLS`, and **no** `pg_write_all_data`. It can already SELECT the two existing private `approvals` and `receipts` tables without an explicit table ACL grant. This is an inherited platform-wide maintenance privilege; ordinary table REVOKE cannot eliminate it.

The revised migration explicitly requires this **existing** global-read/no-global-write baseline and rejects any direct INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES or TRIGGER permission for `postgres` and all DML for issuer/attestor/HTTP/preparer roles. The PostgreSQL17 fixture reproduces the existing inherited read privilege and checks it, rather than falsely claiming that a NOLOGIN owner makes every table unreadable by the shared maintainer. **The sidecars must remain EMPTY and runtime issuer paths OFF until the privileged Hub database connection is separately restricted and independent operator signing consent is proven.** This migration does not increase the shared role's global privileges or activate anything.
