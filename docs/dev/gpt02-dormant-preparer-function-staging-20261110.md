## Security boundaries in one transaction

`scripts/dev/gpt02-dormant-preparer-function-locked.sql` is a single CST-DEV-only PostgreSQL transaction, bounded by a 4-second lock timeout and 15-second statement timeout. It requires: authenticated `postgres` non-superuser with CREATEROLE, exact one inert admin-only grant for the NOLOGIN owner from Supabase's `supabase_admin`, no effective SET/INHERIT membership; one empty and FORCE-RLS staging table owned by `gpt02_core_prep_owner`, exactly two parent FKs, no existing operational or dormant function; NOLOGIN owner and preparer; no direct parent Hub/Core DML held by owner; empty approval/nonce/private staging and no prepared Hub jobs; the validated CHECK requiring task ID greater than 136.

The migration temporarily grants the no-login owner role with `SET TRUE` to shared maintenance `postgres`, changes to that owner for the *function creation only*, and immediately revokes all PUBLIC, anon, authenticated, service_role and preparer `EXECUTE` rights from the new function. It then `RESET ROLE` and revokes the temporary membership via `GRANTED BY postgres` before committing. The final catalog assertion requires exact original owner grantor graph, zero effective SET/INHERIT rights, SECURE DEFINER owner `gpt02_core_prep_owner` and pinned `search_path=pg_catalog`, absence of any operational `prepare_core_task` function, zero parent DML permissions for the no-login owner, zero preparer schema USAGE, and no ability for `postgres`, anon/authenticated/service_role or preparer to execute the dormant function. Any failed pre/post check aborts all grants and DDL.

A SECURITY DEFINER function is inherently privileged; **no public/user/runtime EXECUTE right is ever granted**. This is not used as a shortcut to bypass RLS. Its owner still lacks Hub/Core parent table privileges. A future separately authorized reviewed change must add only the required owner privileges, a distinct authenticated preparer LOGIN with dedicated credentials (not the Hub's shared `postgres` DSN), a signed operator admission/nonce and issuer lease. Nothing in this stage turns on the existing GPT02 lifecycle POST, automatic continuation or a DELL worker.

**Root-cause prevention:** the original generated SQL contained explicit `BEGIN` and `COMMIT` inside a call to Supabase `apply_migration`. Because the DDL can commit before Supabase writes migration metadata, a later metadata/version failure need not roll back the function. The source generator now emits *transaction-body-only SQL*: no explicit BEGIN/COMMIT. The isolated PostgreSQL runner explicitly supplies BEGIN/COMMIT externally, reproducing the migration manager's intended atomic transaction. A source contract test rejects transaction-control statements in the generated SQL. A future migration manager must never accept embedded early commits for this flow.
