# GPT02 CST-DEV: private preparation schema staged, no dispatch authority

## Source and scope

This is deliberately a **non-operational** foundation. The previously reviewed migration created only `gpt02_core_prep_login` as `NOLOGIN`, with no password, no memberships, no table rights and past expiry. Its approval and physical command authority are unchanged. User-approved Task136 (`WA-2611-4633`) already completed one text-only DELL command with final ACK. Task135 is a historical failed execution: do not replay, approve or backfill either task. No PROD changes.

`gpt02-private-preparation-staging-inactive.sql` is a *new* CST-DEV-only migration candidate. It creates NOLOGIN role `gpt02_core_prep_owner` without elevated permissions, private unexposed schema `gpt02_stage`, and an **empty** `core_preparations` staging table. The table has tenant default-only constraint, task ID strictly greater than 136, exact separate UUID foreign keys to existing Hub `public.ai_execution_jobs` and Core `ai_platform.ai_coding_tasks`, unique candidate command/attempt IDs, a unique tenant/task primary key and config SHA-256. Mandatory RLS+FORCE RLS permits only its NOLOGIN owner; a trigger rejects UPDATE/DELETE/TRUNCATE even by the owner. PUBLIC and dormant preparer receive no schema/table/function permissions.

The only function `gpt02_stage.preparation_contract_version()` is **SECURITY INVOKER**, returns integer 1, has NO PUBLIC or preparer EXECUTE privilege, and does not access data or issue commands. The append-only trigger helper is also SECURITY INVOKER with no direct EXECUTE grant. **The operational `prepare_core_task` SECURITY DEFINER function is deliberately NOT deployed**, because the dedicated login cannot authenticate independently and the signed operator/nonce/issuer path remains closed. This distinguishes a safe schema foundation from working lifecycle preparation. No credential login probes, passwords, role activation, extra RLS changes to existing tables, app deploy or session rotation.

## Tests

The exact staged SQL runs against a fresh PostgreSQL16 `--network none` disposable container after applying the same NOLOGIN preparer fixture. Schema table count=1, FORCE RLS=true, empty table, zero SECURITY DEFINER functions, login remains disabled. Direct grants to PUBLIC/preparer are all false. Applying the DDL a second time fails closed; inserting a historical task136 is rejected; even an empty TRUNCATE is blocked by the immutable ledger trigger. SQL lacks direct writes to Hub/Core tables and does not install an operational preparer. Static contract tests validate strict scope, constraints, FK, lack of grants, two invoker-only helper routines and preservation of the existing API lifecycle/`prepared` execution holds.

`gpt02-lifecycle-live-preflight.cjs` now reports `schemaState.dormantPreparationTableStaged` **separately** from `schemaState.preparationInstalled`: the latter remains false while no actual `prepare_core_task` function is installed. The readiness tool is read-only and never grants approval, lease or dispatch regardless of these flags. CI adds the disposable Postgres fixture and static test **inside the existing Core-preparation CI step** to avoid the earlier workflow-file failure from adding too many steps.

## Follow-up and boundaries

The schema is NOT operational merely because it exists. Next requirements: separately authenticated minimal preparer login with verified actual permissions; reviewed least-privilege single-transaction Core+Hub `prepare_core_task` implementation; real independent Super Admin and Core operator signatures bound to a new task; atomic nonce consume; valid issuer lease; exactly one authorized DELL native command with final ACK and independent readback. Keep existing developer `postgres` application connection unchanged until separate module regression proves a restricted cutover. No old #135 or #136 replay; no PROD deployment. Release decision stays **NO_GO**.
